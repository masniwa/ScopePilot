# 診断優先度（採点方式 4）

通信補完後のBase64形式のJSON応答も、サイズ上限・UTF-8・取得エラーを確認して差分比較へ使用する。不正・不完全な応答を変更前の基準にしない。同じ捕捉・同じURL・同じ認証文脈・要求前に完了した応答という比較条件は維持する。

候補レビューの「優先度」は、探索・取込で観測したリクエストの内容と、案件に添付した入力ドキュメントを根拠に、先に診断する機能を選ぶ0〜100の指標である。選択したガイドラインの確認観点を使うが、点数と重みはScopePilot独自のものとする。脆弱性がある確率、深刻度、診断済みかどうかを表す値ではない。

## 採点資料

- 観測通信：URL・メソッド・応答・ロール・画面入力欄に加え、取得済みHARの要求ヘッダーの名前、本文の項目名、情報種別、限定した操作語を使う。JSON、フォームURLエンコード、multipartの項目を解析する。
- 要求内容：個人情報、金額・決済、ロール・権限、認証情報、ファイル送信、外部接続先、AI入力の項目・形式を識別する。`action=delete`や`role=admin`など、許可した固定の操作語も使う。入力値一般を保存・AIへ複写する機能ではない。パスワード、トークン、Cookie、個人情報の実値、ファイルの中身は新しい採点用データへ残さない。通信原本は従来の証拠保存に従う。
- 入力ドキュメント：既存の文書読取AIが抽出したエンドポイント、重要機能・データの優先規則、出典を、実際の要求URL・本文項目・操作語・情報種別と照合する。文書の本文ハッシュが現在の添付資料と一致する抽出だけを使う。
- ガイドライン：案件で有効なものだけを加点根拠へ使用する。同じ確認観点を複数資料が扱っていても、その選択数だけでは加点を増やさない。AISVSはAI機能の手掛かりがある場合、Cloud Native Top 10は関連構成の手掛かりがある場合の条件付き参考とする。

同一URL構造の通信は、最も優先度の高い観測条件を代表として採点する。要求本文の項目や情報種別は、同じ送信先への繰り返し通信でも保持する。回数だけで点数を増やさない。

JSONの全項目をまとめて送り直す要求では、同じHAR内の同一URL・同一認証文脈で、先に受信完了したJSON応答と比較できる場合に、変更された項目を重要機能・データの加点と文書照合に使う。例えば、表示設定を保存する際に未変更の権限設定が同梱されても、それだけで権限変更の加点をしない。要求全体の入力点は保持する。差分はサーバーが変更を反映した証明ではない。

比較できない通信は、変更の有無を未確認として要求全体の情報種別を使う。通信ごとの採点根拠を保持し、比較済みの表示設定と、比較できない別の権限入力が集約されても後者を消さない。同じ送信イベントの再解析だけを置き換え、保存する根拠には項目名・情報種別・許可した固定操作語と識別用ハッシュを使う。認証情報や変更前後の実値は採点用データへ保存しない。

## 点数

基本は20点とし、判断材料が不足している通信を自動的に0点へ落とさない。以下の主要観点は、選択したガイドラインが根拠を持つものから最大1件を加点する。

| 主な観点（URL・要求内容からの手掛かり） | 加点 |
| --- | ---: |
| 権限境界、利用者データ、ロール・権限の指定 | 50 |
| 認証・セッション、認証項目 | 45 |
| 購入・承認・金額・口座等の重要な業務処理 | 45 |
| 個人情報の項目・形式、外部接続先 | 40 |
| ファイル、削除・更新の操作指定、AI入力、運用・クラウド機能候補 | 35 |
| 検索・入力 | 20 |
| API形式 | 15 |

そのうえで、異なる観点の観測材料を一度ずつ加点する。

| 追加の観測材料 | 加点 |
| --- | ---: |
| GET / HEAD / OPTIONS以外の要求 | 12 |
| クエリ、本文項目、画面入力欄 | 10 |
| オブジェクト識別子 | 10 |
| 401 / 403応答 | 8 |
| 5xx応答 | 8 |
| 認証済みとして記録されたロール | 5 |
| 異なる複数の認証済みロール名での観測 | 5 |
| リダイレクト応答 | 5 |

文書で高優先と抽出された機能・データが観測通信と対応した場合、少なくとも80点とする。通常の文書記載との対応は5点を加える。複数文書や複数規則に一致しても文書分を重複加点しない。最大100点へ丸める。URL・項目名・画面の記載による機能推定は、実装の確認とは区別する。

401/403という応答だけでは、権限管理機能として50点を加えない。応答由来の8点を使い、実際のURLや要求内容に別の権限管理の手掛かりがある場合は主要観点も評価する。ログイン等のURLは、`accounts`等の語だけで認証機能より高い権限管理の加点をしない。「未認証」「認証状態未確認」と認証済みロール名の組合せだけでは、複数ロールの5点を加えない。

## 0点と手動判断

通常の静的アセット、または画面確認済みで入力点・重要機能の手掛かりがない単純なHTMLは、従来の一次選定に沿って0点の除外候補にする。ただし、エラー応答、本文・入力点、権限やファイル機能の手掛かり、文書での機能記載がある通信を、ファイル拡張子だけで0点にしない。本文が未取得、または解析不能なら、その制約を理由へ明記する。

静的ファイルの末尾名に含まれるlogin・user・payment等の語だけでは、認証・権限・決済機能とは判定しない。例えば`/css/login.css`や`/images/login_logo.png`は通常の静的参照として扱う。上位ディレクトリーのAPI・利用者・ファイル処理、ID、入力、認証ヘッダー、異常応答等の手掛かりは保持する。

0点も安全性の証明ではない。共通ヘッダー・静的配信設定の診断等は別途必要になる。優先度と利用者による採用・除外は別であり、再計算しても手動の判断を変更しない。高得点の操作が案件の禁止操作に該当していても、優先度によって探索の禁止を解除しない。

## 再計算・保存・帳票

候補一覧は優先度の高い順に表示する。採点理由と参照した文書・基準は下部の詳細に表示する。既存案件を開いたときは、保存済みの観測情報からメモリー上で再採点し、「確信度」は自動選定根拠の明確さとして維持する。優先度は従来の「判定」列に代わって表示する。開いただけでは案件ファイルを書き換えない。

［候補・優先度を再計算］では、案件内に保存済みのHARから要求内容を補い、添付資料に有効な抽出がない場合は設定済みの文書読取AIを使う。その後で候補と優先度を作り直す。新しい探索通信は送らない。添付資料の文書ヒントがない・失敗した・古い場合、その文書を反映したとは扱わない。手動保存で新しい優先度・理由・採点方式番号を案件に保存する。

JSON / HTML / TSVの候補出力も数値優先度と理由を使い、候補の確信度を維持する。診断所見やZAP警告の「確信度・確度」は別の評価であり変更しない。

## 候補の単位、一括採用、Burp連携

同じHTTPメソッドとURL構造の観測通信は1候補にまとめる。ただし、action / operation / op / command / cmd / method / _method / function / fn / do / intent / mode / event / task / dispatch / operationName等の処理指定は値を区別する。リソースIDや通常の入力値を一律に残して候補を増やすものではない。本文内の処理値は識別用ハッシュと短い操作名として記録し、本文を丸ごと複写しない。従来1件に統合していた処理を分割した新しい候補へ、旧パターンの採用・除外を一律に引き継がない。

1候補1行の一覧に、代表通信に対応するBurp Proxy historyのRequest IDを1つ表示する。照合はネイティブIDを返す読取APIを使い、メソッド・URL・本文・Cookie/Authorizationのフィンガープリントを照合する。ID未照合・API未対応は明示する。ScopePilot内部ID、LoggerのID、履歴のoffsetや行番号を代用しない。IDは接続中のBurpプロジェクトに属するため、プロジェクト切替後は照合し直す。

［上位N件］は優先度降順・同点はパターン順で指定件数だけ採用し、［N点以上］は閾値を含む候補だけ採用する。どちらも全候補に適用し、それ以外の採用チェックを外す。検索中の表示件数に限定しない。Nの不正入力では変更しない。採用変更は明示保存する。

［Burp+mcp+AIプロンプト］は、採用済み候補のIDを優先度降順に並べ、重複IDを除いてカンマ区切りにする。採用なし・未照合IDありでは空欄と理由を表示し、コピーを無効にする。生成はテキストの作成のみで、Scan開始や設定反映はしない。既存のBurp Scope出力はURL範囲の設定なので、本文の処理条件までは制限しない。処理別の引き渡しにはIDプロンプトを使う。

## 参照元と適用範囲

ガイドラインの確認観点から採点ルールへの対応はScopePilotの解釈であり、公式のリスク採点表ではない。要件の適合・違反を判定したものでもない。本文を複製せず、次の一次資料を参照する。

- [WebAppPentestGuidelines](https://github.com/WebAppPentestGuidelines/WebAppPentestGuidelines)：認証、認可、入力・ファイル等の手動診断観点。
- [OWASP Top 10:2025](https://top10.owasp.org/2025/0x00_2025-Introduction/)：A01認可・SSRF、A05入力、A06業務設計、A07認証、A10例外処理等。
- [OWASP ASVS 5.0](https://asvs.owasp.org/)：認証・セッション、認可、入力、API、ファイル、エラー等の検証観点。表示するV番号は章単位の参考で、要件を検査済みという意味ではない。
- [OWASP WSTG 4.2](https://wstg.owasp.org/v4.2/4-Web_Application_Security_Testing/)：エントリーポイント、認証、認可、入力・業務ロジック等。
- [OWASP AISVS 1.0](https://github.com/OWASP/AISVS/tree/main/1.0)：案件設定で指定している版を使用。AIの入力・権限等の条件付き確認観点。別の最新版へ自動移行しない。
- [OWASP Cloud Native Application Security Top 10](https://owasp.org/projects/cloud-native-application-security-top-10)：クラウド構成・認証認可等の条件付き参考。暫定資料であり、対象構成の確認が必要。
- [デジタル庁DS-221](https://www.digital.go.jp/resources/standard_guidelines#ds221)：フォーム・API、認証・アップロード等のリスクに応じた診断対象選定。案件への適用は担当者が判断する。

具体的な検証方法と合格条件は[testing.md](../testing.md)を参照する。
